## 1. SEGURANÇA

### S1 — `delete-unconfirmed-user` sem autenticação **[P0]**

**Arquivo:** `supabase/functions/delete-unconfirmed-user/index.ts`  
**Problema:** A função usa `SUPABASE_SERVICE_ROLE_KEY` e chama `auth.admin.listUsers()` + `auth.admin.deleteUser()`, mas **não valida nenhum token Bearer** antes de executar. Qualquer requisição HTTP com um email válido apaga a conta.

```ts
// Linha 15 — lê email direto do body sem autenticar o chamador
const { email } = await req.json().catch(() => ({ email: null }))
// Linha 63 — deleta com service_role sem checar quem pediu
await supabase.auth.admin.deleteUser(user.id)
```

Agravante: a função também não está no `config.toml`, portanto usa `verify_jwt = true` implícito do Supabase — mas isso valida apenas que o JWT é válido, **não que o chamador é o dono do email**. Um usuário autenticado pode deletar a conta de outro usuário passando o email alvo.

**Correção necessária:** Após validar o JWT, verificar que `user.email === email` informado no body (ou que o chamador é admin).

---

### S2 — `delete-user-data` com `verify_jwt = false` **[P1]**

**Arquivo:** `supabase/config.toml:10`  
A função faz validação manual via `supabase.auth.getUser(token)` (correto), mas `verify_jwt = false` significa que o Supabase não rejeita requests malformados antes do código rodar. Se houver qualquer bug no bloco de validação manual, o fallback é sem proteção.

**Recomendação:** Mudar para `verify_jwt = true` e remover o bloco manual de validação, deixando o Supabase gerenciar — ou manter `false` apenas se a validação manual for intencionalmente necessária (ex.: tokens customizados).

---

### S3 — `Access-Control-Allow-Origin: "*"` em todas as edge functions **[P1]**

Todas as funções retornam `"Access-Control-Allow-Origin": "*"`. Para funções que processam pagamentos (`create-payment`, `mercadopago-payment`, `pagbank-payment-v2`, `efi-payment`), o ideal é restringir à origem de produção (`https://urebrasil.com.br`).

## 2. FLUXO DE AQUISIÇÃO

### F1 — Duas fontes de verdade para navegação **[P1]**

`useOnboardingGuard` (baseado em `current_onboarding_step` no banco) e `goToStudentCardFlow()` (recalcula estado a partir de dados reais) podem divergir se triggers de banco falharem silenciosamente. Não há reconciliação entre os dois mecanismos.

**Cenário de falha:** usuário completa pagamento → trigger atualiza `current_onboarding_step` mas falha → `useOnboardingGuard` redireciona para `/pagamento` novamente → loop infinito percebido pelo usuário.

---

### F2 — `selected_plan_id` exclusivamente em localStorage **[P1]**

Plano selecionado em `EscolherPlano.tsx` é gravado apenas em `localStorage`. Se o usuário troca de dispositivo, abre em aba anônima, ou limpa dados do browser antes de completar o pagamento, o `selected_plan_id` é perdido e o fluxo quebra sem mensagem clara.

Não há fallback buscando o plano do banco (ex.: último plano associado ao perfil).

---

### F3 — Polling PIX sem reconexão após perda de rede **[P2]**

**Arquivo:** `src/pages/PagamentoPix.tsx:58`  
O `setInterval` de 5s não trata falhas de rede — se a conexão cair por alguns segundos, o erro é silenciado (`return` no catch) e o polling continua tentando. Não há lógica de backoff ou notificação ao usuário de "sem conexão". Se o pagamento for confirmado durante uma janela de falha de rede, o usuário não é redirecionado automaticamente.

---

### F4 — `PaymentSuccessPage` depende de múltiplos estados frágeis **[P2]**

**Arquivo:** `src/pages/PaymentSuccessPage.tsx`  
A página lê `location.state` + `localStorage("recent_payment_id")` + `useAuth`. Se qualquer um estiver ausente (F5, sessão expirada), a página renderiza sem dados de confirmação. Não há redirect de fallback como foi adicionado no PagamentoPix.

---

### F5 — Fluxo de upsell físico sem validação de duplicata **[P2]**

**Arquivo:** `src/pages/Checkout.tsx`  
O checkout de upsell não verifica se já existe um pagamento aprovado para cartão físico antes de processar. Um duplo-clique rápido ou retry de rede pode gerar dois pagamentos para o mesmo upsell.

### Q3 — Duplicação de lógica de pagamento **[P2]**

`Pagamento.tsx`, `Checkout.tsx` e `CheckoutFisica.tsx` têm lógica quase idêntica para:
- Inicialização do CardForm do Mercado Pago
- Chamada às funções `mercadopago-payment`, `pagbank-payment-v2`, `efi-payment`
- Atualização de `current_onboarding_step` pós-pagamento

Essa triplicação aumenta superfície de bug: uma correção em um arquivo precisa ser replicada nos outros dois manualmente.

### E2 — `verify-student-card` é pública por design **[info]**

A função é chamada diretamente via URL pública (sem Bearer token) para validação de QR Code por terceiros. Isso é intencional. Verificar se há rate limiting configurado no Supabase para evitar enumeração de cartões.

### E3 — `cleanup-rejected-documents` sem agendador confirmado **[P2]**

A função descreve `pg_cron/pg_net` como trigger, mas não há migration com `cron.schedule()` visível nas migrations do projeto. Se não estiver agendada no banco, documentos rejeitados nunca são limpos.

Existe `mercadopago-webhook` para confirmação assíncrona de pagamentos MP. Não foi identificado webhook equivalente para Efi (banco Inter/Gerencianet). Pagamentos Efi que ficam pendentes não têm mecanismo de atualização assíncrona de status.
